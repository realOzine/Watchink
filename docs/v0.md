## 1. v0 范围与非目标

v0 交付的产品结果：用户可以从桌面、Web、CLI、MCP 中任一入口导入一个本地视频，或一个 YouTube / Bilibili 单视频链接。程序依次完成获取媒体、提取音频、本地转写、在线生成笔记，得到一份带时间引用的中文 Markdown 笔记。之后可以从任一入口读取同一份结果，跳回原视频核对，并导出。

| 包含 | 不包含（去向） |
| --- | --- |
| 本地文件、Web 上传、YouTube / Bilibili 无需登录的单视频 | 播放列表、需要登录或会员的视频、其他站点（候选） |
| whisper.cpp 本地转写（macOS 使用 Metal，Windows / Linux 使用 CPU） | Windows / Linux GPU 加速（v2 运行时管理） |
| OpenAI 兼容在线文本模型生成中文笔记 | 本地文本模型的验收（v2）。v0 允许配置本地 OpenAI 兼容端点，但不验收、不承诺效果 |
| 查看笔记和字幕、跳转引用、导出 Markdown / SRT / VTT / TXT / JSON | 搜索、画面理解（v1）；笔记编辑、问答（v2） |
| 查看任务、取消、重试、重启后续跑 | 批量导入界面、并发与资源配额配置（v2） |
| MCP stdio | MCP Streamable HTTP（v1） |
| 单窗口桌面应用 | 托盘、全局快捷键、多窗口、自动更新（v2 或候选） |
| 仅本机访问 | 远程访问、账号、同步（v0–v2 均不包含） |

## 2. 与前期讨论的差异

前期讨论给出了总体方向。本文按 roadmap 的约束做了以下调整：

| 主题 | 前期讨论 | v0 结论 | 原因 |
| --- | --- | --- | --- |
| 发行形态 | 纯 Go 无界面版和 Wails 桌面版两个产物 | 每个平台一个发行物，同时承载桌面、服务、CLI、MCP（D-02）。纯 Go 无界面构建只作为补充产物，不是发布门槛 | roadmap §2.1 要求同一发行物提供全部运行方式 |
| Wails 版本 | 倾向 v3 | v0 采用 v2 稳定版（D-03） | roadmap 要求默认先评估稳定版；v0 只用到 Wails 很小的功能面，将来迁移成本有限 |
| 事实来源 | Markdown 文件是唯一事实来源，SQLite 只是派生索引 | SQLite 加文件产物是事实来源，Markdown 是渲染和导出结果（D-05） | 引用必须由程序校验，还要保证多版本、多入口的一致性；Obsidian 兼容通过导出实现 |
| 单实例 | 先启动的进程成为 Engine | Engine 始终是独立的后台进程（D-01） | 如果由客户端兼任 Engine，MCP 或 CLI 退出时会把正在运行的任务一起带走 |
| 本地模型 | A / B / C 三档 | v0 内嵌自建的 whisper.cpp 做本地 ASR，文本生成走在线模型；托管本地推理 sidecar 放到 v2 | roadmap 对 v0 只要求“本地 ASR + 在线笔记”这条最小混合路径 |
| 在线模型接入 | 分别使用各家官方 SDK | 只实现 OpenAI 兼容协议，自写一个薄客户端（D-08） | 一个协议就能覆盖多数在线服务和本地端点 |
| MCP 传输 | stdio 和 Streamable HTTP | v0 只做 stdio，HTTP 放到 v1（D-12） | 本机 agent 用 stdio 已经够用；HTTP 需要更大的鉴权面 |
| 前端 | htmx 或 SPA | React + TypeScript SPA（D-17） | roadmap 的技术基线；桌面和 Web 共用同一套前端 |
| 画面、搜索、向量 | 第二个里程碑 | v1 | roadmap 的版本划分 |

## 3. 关键设计决策

| ID | 决策 | 主要放弃的方案 | 验证 |
| --- | --- | --- | --- |
| D-01 | Engine 作为独立进程运行，四个入口都是它的客户端 | 各入口直接打开数据库；由第一个启动的入口兼任 Engine | S-09 |
| D-02 | 每个平台一个发行物，承载全部运行模式；另外提供纯 Go 无界面构建作为补充 | 桌面版和 CLI 版作为两个必需产物 | S-01、S-02、S-03 |
| D-03 | 使用 Wails v2，并尽量缩小对 Wails 的依赖面 | Wails v3 beta | S-01 |
| D-04 | 前端传输以 HTTP 为主，Wails 绑定只用于原生能力 | 业务调用走 Wails 绑定 | S-04、S-05 |
| D-05 | SQLite 加文件产物作为事实来源 | Markdown 文件作为唯一事实来源 | — |
| D-06 | whisper.cpp 自行构建并内嵌；FFmpeg、yt-dlp、Deno 按需下载，锁定版本并校验 | 全部内嵌；全部要求用户自行安装 | S-06、S-07 |
| D-07 | 以 whisper.cpp CLI 子进程整段转写 | 常驻 whisper-server；切片并行 | S-06 |
| D-08 | 只实现 OpenAI 兼容 Chat Completions，自写客户端 | 引入多家官方 SDK | S-10 |
| D-09 | 笔记生成：分块 map → reduce（只引用要点）→ 程序校验与渲染 | 整段字幕一次交给长上下文模型 | — |
| D-10 | 时间统一用毫秒；引用基于片段 ID，内部链接为 `wk://seg/` | 由模型输出时间戳 | S-11 |
| D-11 | 播放：能直接播放就直接播放，否则优先无损重封装，必要时转码为 H.264 | 为 Linux 额外生成 WebM | S-05、S-11 |
| D-12 | MCP 使用官方 Go SDK，v0 只提供 stdio | v0 同时提供 Streamable HTTP | A06 |
| D-13 | 本地文件复制进库，用抽样哈希去重 | 原地引用；导入时计算全量哈希 | — |
| D-14 | 凭据从环境变量或独立的 0600 文件读取 | 系统钥匙串 | — |
| D-15 | 仅本机访问；桌面、CLI、MCP 用令牌鉴权；Web 界面可选、默认关闭、开启后免登录；严格限定读写路径 | 始终开放的无鉴权 localhost 服务；一次性登录码加 cookie（已移除） | — |
| D-16 | Go 依赖以标准库为主，第三方库限定在一份清单内 | LLM 编排框架、ORM、Web 框架 | — |
| D-17 | 前端：React + TypeScript + Vite，不引入大型组件库 | htmx + templ | — |
| D-18 | 调度：阶段 DAG + 资源信号量 + 指纹复用 | 线性脚本加整任务重跑 | — |

### D-01 Engine 作为独立进程，四个入口都是客户端

- **选择**：同一个数据目录在同一时刻只运行一个 Engine 进程。它独占 SQLite 写入、任务调度、外部工具进程和 HTTP 服务。桌面窗口、浏览器、CLI 和 MCP stdio 进程都通过本机 HTTP 调用它。客户端发现没有 Engine 时会自动拉起一个。
- **放弃**：(a) 各入口各自打开数据库并调度，会导致重复处理和写锁冲突；(b) 让第一个启动的入口兼任 Engine，那么 MCP 客户端或 CLI 退出时，正在运行的任务也会随之终止，违反 roadmap 中“MCP 断开不默认取消后台任务”的约束。
- **代价**：多了一个后台进程，需要处理 Engine 发现、竞争启动、版本不匹配、空闲退出和孤儿子进程。具体规格见 §5。

### D-02 每个平台一个发行物，承载全部运行模式

- **选择**：同一个可执行文件（macOS 上是 `.app` 内的可执行文件）通过子命令切换运行模式。无参数或 `desktop` 时打开窗口；`serve`、`web`、`mcp` 以及其余 CLI 命令都不初始化 GUI。另外以 `CGO_ENABLED=0 -tags nogui` 构建一个纯 Go 的无界面版本，供没有 WebKitGTK 的 Linux 服务器等环境使用。这个版本作为补充产物发布，不计入 v0 发布门槛。
- **放弃**：把桌面版和 CLI 版作为两个必需产物，这不满足 roadmap §2.1。
- **代价**：
  - GUI 构建依赖 cgo，必须在三个平台的原生 runner 上分别构建。
  - 在 Linux 上，即使以无窗口模式运行，系统里也必须有 GTK / WebKitGTK 动态库，这一点要写进发行说明。
  - Windows 存在 GUI 子系统与控制台子系统的取舍（S-02）。

### D-03 使用 Wails v2

- **选择**：v0 使用 Wails v2 当前的稳定版（查阅时为 v2.15.x，实施时锁定）。Wails 相关代码只放在 `internal/entry/desktop` 中，桌面能力只通过 6 个绑定方法暴露（§13.6）。Linux 构建使用 `webkit2_41` 构建标签（Ubuntu 24.04 已不再提供 webkit2gtk-4.0）。
- **放弃**：v3 beta。v3 的多窗口、services、托盘更适合 v2 版本里的桌面增强，但 v3 目前仍处于预发布阶段，而且以 nightly 节奏频繁发布。v0 只需要单窗口，用不到这些能力。
- **代价**：将来迁移到 v3 时需要改写 `internal/entry/desktop`，预计只涉及启动流程、窗口选项和绑定。业务代码和前端不受影响。
- **复评时点**：v1 开始前。如果 v2 版本需要多窗口或托盘，届时根据 v3 的状态决定是否迁移。

### D-04 前端传输以 HTTP 为主

- **选择**：桌面和 Web 共用同一套前端代码和同一套 HTTP 接口，包括：
  - REST 调用。
  - 用 fetch 流式读取的 SSE 格式事件流。
  - 带签名短期令牌、支持 Range 请求的媒体 URL。

  桌面前端从内嵌资源加载，通过绑定方法 `EngineInfo()` 拿到 Engine 地址和令牌，之后直接访问 `127.0.0.1`。Wails 绑定只负责原生能力：选择文件、保存文件、在文件管理器中显示、打开外部链接、提供 agent 接入信息。
- **放弃**：让业务调用走 Wails 绑定。那样需要为桌面单独维护一套接口，而 Web 端用不了。
- **代价**：WebView 跨源访问 loopback 地址需要配置 CORS。macOS 需要确认 App Transport Security（ATS）是否放行，Windows（Chromium 内核）需要响应私有网络访问预检。
- **回退方案**（S-04 不通过时）：桌面端经 Wails AssetServer 的 `Handler` 反向代理到 Engine，变成同源访问；进度推送改为桌面 Go 侧订阅 Engine 事件，再转发为 Wails 事件；媒体仍走 loopback。前端只需替换 `transport` 模块。

### D-05 SQLite 加文件产物作为事实来源

- **选择**：SQLite 只由 Engine 打开，保存视频、任务、阶段、字幕片段、笔记版本、引用和产物登记。大文件放在数据目录里，在数据库中用相对路径和 sha256 登记。这些大文件包括媒体、ASR 原始输出、笔记的 Markdown 与 JSON、分块中间结果。笔记的结构化 JSON 是生成结果的规范形式，Markdown 由程序渲染得到。
- **放弃**：以 Markdown 文件为唯一事实来源。这样无法可靠地校验引用；多个入口并发写入时需要文件监控和冲突处理；而 v0 本身也不提供编辑。
- **代价**：用户直接修改数据目录里的 Markdown，程序不会感知。Obsidian 等工具通过导出使用笔记。v2 的编辑功能会在这套结构上做版本化。
- **驱动选择**：`modernc.org/sqlite`（纯 Go）。GUI 构建和无界面构建使用同一个驱动，行为保持一致。

### D-06 外部工具：自建 whisper.cpp 并内嵌，其余按需下载

- **whisper.cpp**：官方 Release 中的预编译命令行程序主要面向 Windows，不能覆盖三个目标平台。因此在 CI 中为三个平台自行构建 `whisper-cli`：静态链接，macOS 上启用 Metal 并内嵌着色器库。构建产物通过 `go:embed` 打进主程序，首次使用时释放到数据目录并校验 sha256。whisper.cpp 的版本随主程序一起锁定，不需要联网即可使用。
- **FFmpeg / ffprobe、yt-dlp、Deno**：第一次用到时，按内置清单下载固定版本，校验 sha256 后安装到数据目录。其中 Deno 只在第一次导入 YouTube 链接时下载，因为 yt-dlp 需要一个外部 JS 运行时来处理 YouTube（官方推荐并默认使用 Deno）。
- **模型**：whisper ggml 模型首次使用时按需下载（固定版本和 sha256），也支持导入本地文件。
- **放弃**：(a) 全部内嵌：FFmpeg 和 Deno 体积较大，而且由我们分发 GPL 版 FFmpeg 会带来许可义务；(b) 全部要求用户自装：不满足“无需手动拼装依赖”。
- **代价**：
  - 主程序增加约数 MB。
  - 需要维护一份工具清单，记录 URL、版本、sha256 和许可。
  - 在 Windows 上释放并执行内嵌的程序，可能触发杀毒软件的启发式检测（S-06）。

### D-07 以 whisper.cpp CLI 子进程整段转写

- **选择**：每个转写任务启动一个 `whisper-cli` 子进程，对整段 16 kHz 单声道 WAV 转写，输出 JSON。先检测语言，再用确定的语言和相应提示词正式转写。VAD 默认关闭：S-06 在 macOS 上实测 whisper.cpp v1.9.5 的 VAD 会把静音之后第一个片段的起始时间提前到静音开头（约 20 s），不满足“时间映射正确”，见 `docs/spikes/v0-p0.md`。用户仍可通过 `asr.vad` 手动开启。
- **放弃**：
  - (a) 常驻 `whisper-server`：能省下每次加载模型的时间（秒级），但多出进程托管、健康检查和取消语义要处理。
  - (b) 切片并行转写：可以细粒度续跑，但会引入切片边界和时间映射的复杂度。roadmap 只要求已成功的阶段不重复执行，整段转写已经满足。
- **代价**：转写中途被打断时需要重跑整段；进度只能依赖 whisper 自身的输出。
- **默认模型**：由 S-06 在三台参考机上实测后确定，不预先承诺速度。

### D-08 在线文本模型只实现 OpenAI 兼容 Chat Completions

- **选择**：只实现一个 `openai-compatible` 适配器，配置项为 `base_url`、`model` 和凭据。结构化输出按 `json_schema` → `json_object` → 仅靠提示词三级降级，结果用 Go 结构体严格校验。客户端基于 `net/http` 自己实现。
- **放弃**：接入多家官方 SDK。v0 只需要一个可用的在线后端；而各家兼容端点对 SDK 发出的额外字段容忍度不一，自写客户端更容易控制。
- **附带结果**：Ollama、LM Studio、llama.cpp server 等本地 OpenAI 兼容端点也能配置使用，但 v0 不验收。

### D-09 分块 map → reduce → 程序校验与渲染

- **选择**：
  1. 字幕按时长和 token 预算切成若干块。
  2. map 阶段逐块产出要点，每个要点只能引用本块内片段的编号。
  3. reduce 阶段只负责组织要点编号，不再接触字幕片段。
  4. 程序负责校验引用、把 reduce 没放进去的要点补回去、计算时间、渲染 Markdown。
- **放弃**：把整段字幕一次交给长上下文模型。这依赖模型能力，长视频的覆盖无法保证，也不满足 V0-R05 “按段处理并汇总”。
- **收益**：
  - 时间由程序根据片段 ID 计算，模型无法编造时间戳。
  - map 产出的内容不会在 reduce 中被静默丢弃。
  - 小上下文模型也能处理长视频。

### D-10 引用与时间轴

所有时间都是相对原视频的毫秒整数。字幕片段有稳定的 ID。笔记中的引用写作 `[mm:ss](wk://seg/<segment_id>)`，导出时按来源改写为平台的时间链接或纯文本时间。片段 ID 格式、`wk://seg/` 链接格式、时间单位均属于**契约**。

### D-11 播放代理

- **选择**：
  - 源文件是 MP4 / MOV 容器、H.264 视频、AAC 或 MP3 音频时，直接播放。
  - 容器不同但编码兼容时，无损重封装。
  - 编码不兼容时，转码为 H.264 / AAC，高度上限 720p。
  - 下载链接视频时优先选择 H.264 / AAC 格式，尽量避免转码。
  - Linux 桌面依赖系统 GStreamer 提供 H.264 / AAC 解码，所需包名写进发行说明。缺少解码器时，界面提示安装，或改用浏览器打开。
- **放弃**：为 Linux 额外生成 WebM。转码耗时会成倍增加，而这个问题装一个系统包就能解决。

### D-12 MCP 使用官方 Go SDK，v0 只提供 stdio

- **选择**：使用 `modelcontextprotocol/go-sdk`（查阅时为 v1.8.x）。`watchink mcp` 以 stdio 方式运行，确认 Engine 已启动后，把工具调用转发给 Engine。共提供 8 个 tools（§13.5），不提供 resources 和 prompts。
- **放弃**：v0 同时提供 Streamable HTTP。那需要额外设计远程鉴权和 Origin 策略，而本机 agent 用 stdio 就够了，HTTP 放到 v1。resources 在不同客户端中的支持程度差异较大，v1 根据读取画面的需求再加。

### D-13 本地文件复制进库，用抽样哈希去重

- **选择**：导入本地文件时把它复制进数据目录，复制过程中顺带计算完整 sha256。去重键使用“文件大小 + 头、中、尾各 4 MiB 的 sha256”，这样导入请求能在毫秒级给出去重结果。链接导入时，在本地规范化 URL，得到平台视频 ID 作为去重键，不需要联网（b23.tv 短链除外）。
- **放弃**：
  - (a) 原地引用：用户移动或删除原文件后，笔记就失去了对应的视频。
  - (b) 导入时同步计算全量哈希：大文件在慢速磁盘上会阻塞数秒到数十秒。
- **代价**：磁盘占用翻倍（导入后用户可以删除原文件）。抽样哈希理论上可能碰撞，需要文件大小相同且三段抽样内容完全相同，实际概率可以忽略。

### D-14 凭据

- **选择**：在线模型的 API Key 按以下优先级读取：
  1. 环境变量 `WATCHINK_LLM_API_KEY`。
  2. 配置项 `llm.api_key_env` 指定的环境变量。
  3. `secrets.toml`：位于用户配置目录，权限 0600，不在数据目录内，因此不会进入备份或导出。

  接口对凭据只写不读，读取时只返回“已配置”和末 4 位。
- **放弃**：系统钥匙串。macOS 对后台进程和未签名程序会弹出访问提示，Linux 上还可能没有 Secret Service，这些都会增加失败路径。v2 再评估。

### D-15 本机安全边界

- 只监听 127.0.0.1，每次启动生成随机令牌，并校验 Host 头以防 DNS rebinding。
- Web 界面是可选功能（`web.enabled`，默认关闭，可在桌面应用的设置里开关）。开启后本机浏览器无需登录即可使用；状态变更请求校验 Origin 和自定义请求头。

- Engine 只在数据目录内写文件。导出到用户指定位置时，由 CLI 或桌面进程自己写入。

详见 §15。

## 5. Engine 与单一调度所有者

### 5.1 发现文件

- `<data>/run/engine.lock`：Engine 存活期间一直持有的独占文件锁。Unix 上用 flock，Windows 上用 LockFileEx。
- `<data>/run/engine.json`：权限 0600，用原子写入（临时文件 + rename）生成。内容示例：

```json
{
  "pid": 12345,
  "base_url": "http://127.0.0.1:47823",
  "token": "<base64url，32 字节随机数>",
  "version": "0.1.0",
  "build_id": "<commit>-<构建日期>",
  "api": 1,
  "mode": "background",
  "started_at": "2026-10-09T08:00:00Z"
}
```

判断 Engine 是否存活只看锁。engine.json 只用来找到地址和令牌：如果能拿到锁，说明没有存活的 Engine，此时 engine.json 视为陈旧。

### 5.2 客户端连接流程

1. 读取 engine.json，带令牌调用 `GET /api/v1/engine`。调用成功且 `build_id` 一致，就使用这个 Engine。
2. 如果 `build_id` 不一致：对方空闲（没有排队或运行中的任务）时，请求它关闭，然后进入第 3 步；否则返回 `ENGINE_VERSION_MISMATCH`，提示用户等待任务完成，或执行 `watchink engine stop --force`。
3. 如果没能连上：以分离模式拉起 `watchink engine run --data-dir <dir>`（Unix 用 `Setsid`；Windows 用 `DETACHED_PROCESS`、`CREATE_NEW_PROCESS_GROUP`、`CREATE_NO_WINDOW`），每 100 ms 轮询一次，最长等待 15 s。
4. 多个客户端同时执行第 3 步时，只有一个新进程能拿到锁，其余新进程立即退出；客户端在轮询中连上胜出的那个 Engine。
5. 指定 `--no-spawn` 时不拉起 Engine，直接返回 `ENGINE_UNAVAILABLE`。

### 5.3 Engine 启动顺序

1. 获取锁。
2. 读取配置。
3. 打开 SQLite 并执行迁移。
4. 执行重启恢复（§7.6）。
5. 监听 127.0.0.1。默认端口 47823；被占用时改用随机端口。
6. 写入 engine.json。
7. 启动调度器，进入就绪状态。

### 5.4 空闲退出与关闭

- **后台模式**（`engine run`）：同时满足以下三个条件时自动退出：没有排队或运行中的任务；没有事件流订阅者；10 分钟内没有 API 请求。时长可通过 `engine.idle_exit` 配置。桌面窗口打开期间会一直订阅事件流，因此 Engine 不会退出。
- **前台模式**（`serve`）：不会因空闲退出。
- **`engine stop`**：停止接收新任务，等待运行中的阶段到达可中断点（最长 10 s）后退出。被打断的任务标记为 `interrupted`，下次启动时自动续跑。加 `--force` 时直接终止子进程。
- **关闭桌面窗口**：只退出桌面进程。Engine 会继续把任务做完，然后空闲退出。有任务运行时，界面会提示这一点。

### 5.5 子进程管理（procx）

| 平台 | 启动方式 | 取消 | Engine 意外退出时 |
| --- | --- | --- | --- |
| Linux | 新进程组，设置 `Pdeathsig=SIGKILL` | 向进程组发 SIGTERM，3 s 后发 SIGKILL | 内核按 Pdeathsig 终止子进程 |
| macOS | 新进程组，经 `watchink _guard` 包装 | 同上 | guard 发现父进程变为 1 号进程后，终止整个进程组 |
| Windows | 加入设置了 `KILL_ON_JOB_CLOSE` 的 Job Object | `TerminateJobObject` | 句柄随 Engine 一起关闭，系统终止整个 Job |

- 子进程一律用参数数组启动，不经过 shell。
- stderr 的最后 64 KiB 脱敏后保存到阶段的错误详情中。
- 每个子进程登记在 `child_processes` 表中，供重启时核对。

## 6. 数据模型与存储

### 6.1 位置

| 平台 | 默认数据目录 `<data>` | 用户配置目录 `<cfg>` |
| --- | --- | --- |
| macOS | `~/Library/Application Support/Watchink/Data` | `~/Library/Application Support/Watchink` |
| Windows | `%LOCALAPPDATA%\Watchink\Data` | `%APPDATA%\Watchink` |
| Linux | `${XDG_DATA_HOME:-~/.local/share}/watchink` | `${XDG_CONFIG_HOME:-~/.config}/watchink` |

### 6.5 SQLite 设置与迁移

- PRAGMA：`journal_mode=WAL`、`synchronous=NORMAL`、`foreign_keys=ON`、`busy_timeout=5000`。
- 写操作经单一连接串行执行，读操作使用独立的连接池。
- 迁移 SQL 用 `go:embed` 打包，按 `PRAGMA user_version` 顺序执行。迁移前先把数据库复制为 `watchink.db.bak-<旧版本号>`。
- 如果数据库版本高于程序所支持的版本，Engine 拒绝启动，并提示用户升级程序。这可以防止旧版程序损坏新版数据。

### 6.6 去重键（契约）

| 来源 | `source_key` |
| --- | --- |
| 本地文件、上传 | `file:<字节数>:<sha256(头 4 MiB ‖ 中 4 MiB ‖ 尾 4 MiB)>`；小于 12 MiB 的文件对全文求哈希 |
| YouTube | `youtube:<11 位视频 ID>`。支持 `watch`、`youtu.be`、`shorts`、`live`、`embed` 形式；忽略 `list=` 等播放列表参数 |
| Bilibili | `bilibili:<BV 号>:p<分 P 序号，默认 1>`。av 号链接在本地换算成 BV 号；`b23.tv` 短链在导入请求中同步解析（超时 5 s） |

其他主机名返回 `UNSUPPORTED_SOURCE`。

## 7. 作业与处理流水线

### 7.1 任务类型

- `process_video`：处理一个视频，即本节描述的流程。
- `prepare_tools`：下载并安装工具或模型（§11），与 `process_video` 共用同一套状态、进度和取消机制。

### 7.2 `process_video` 的阶段

| 阶段 | 依赖 | 资源类 | 动作 | 产物 | 指纹输入 |
| --- | --- | --- | --- | --- | --- |
| `ensure_tools` | — | net | 检查本任务所需的工具和模型；缺失且允许自动准备时下载 | — | — |
| `acquire` | ensure_tools | net / io | 复制本地文件、接收上传，或用 yt-dlp 下载 | source | source_key、下载格式策略版本 |
| `probe` | acquire | io | 用 ffprobe 读取时长、流信息、起始时间 | probe | 源文件 sha256 |
| `extract_audio` | probe | media | 提取 16 kHz 单声道 WAV，计算时间偏移 | audio | 源文件 sha256、ffmpeg 版本、参数 |
| `transcribe` | extract_audio | asr | 语言检测、整段转写、后处理，生成字幕版本 | asr_raw | 音频 sha256、whisper 版本、模型 sha256、语言、提示词、VAD 参数 |
| `playback` | probe | media | 判断能否直接播放：直接使用、重封装或转码 | playback | 源文件 sha256、策略版本、ffmpeg 版本 |
| `note_map` | transcribe | llm | 分块，逐块生成要点（按块缓存） | map_chunk × N | 字幕版本 ID、块边界、提示词版本、模型标识、温度 |
| `note_reduce` | note_map | llm | 组织章节、概览和结论 | reduce | 全部 map 产物的哈希、提示词版本、模型标识 |
| `note_render` | note_reduce | cpu | 校验引用、补回要点、渲染，登记新的笔记版本 | note_md、note_json | reduce 产物哈希、渲染器版本 |

- 全部阶段成功后，任务状态才变为 `succeeded`。
- `note_render` 一完成就可以读取笔记，此时 `playback` 可能仍在进行。
- 总进度按以下权重计算：ensure_tools 2、acquire 15（本地文件为 2）、probe 1、extract_audio 4、transcribe 45、note_map 25、note_reduce 7、note_render 1。`playback` 不计入总进度，单独显示。

### 7.3 状态机（契约）

- **任务状态**：
  - 正常流程：`queued` → `running` → `succeeded` / `failed` / `cancelled`。
  - 取消：`running` → `cancelling` → `cancelled`。
  - Engine 意外退出后：`running` → `interrupted`；启动恢复时，如果 `engine.auto_resume` 为 true（默认），再变回 `queued`。
- **阶段状态**：`pending` → `running` → `succeeded` / `failed` / `cancelled`；命中缓存时直接变为 `succeeded`，并记 `reused=true`。

| 操作 | 允许的任务状态 | 结果 |
| --- | --- | --- |
| cancel | `queued`、`running` | `queued` 立即变为 `cancelled`。`running` 先变为 `cancelling`，等所有运行中的阶段停止后变为 `cancelled`。最长等待 10 s，超时则强制终止，并记录 `forced=true` |
| retry | `failed`、`cancelled`、`interrupted` | 沿用同一个 `job_id`，`attempt` 加 1，状态回到 `queued`。产物仍然有效的已成功阶段会被跳过 |
| 其他组合 | — | 返回 `CONFLICT` |

每次状态变化都写入 `job_events`，并递增任务的 `rev`，供长轮询和事件流使用。

### 7.4 指纹与产物复用

```text
fingerprint = sha256(规范化 JSON {stage, stage_version, inputs, params, tool_versions, model_ids})
```

阶段执行前，先按 `(kind, fingerprint)` 查找已登记的产物。如果记录存在、文件存在、sha256 也一致，就复用该产物并跳过本阶段；如果产物的文件已按策略删除（`purged=true`），则重新执行本阶段。阶段逻辑发生变化时，递增它的 `stage_version`。

举例：修改模型配置后重试，`note_*` 阶段的指纹会变化，因而重新生成；下载和转写阶段的指纹不变，不会重复执行。这正是 V0-A07 要求的行为。

### 7.5 重复导入策略（契约）

| 情况 | 结果 |
| --- | --- |
| `source_key` 不存在 | 新建视频和任务，返回 `status: queued` |
| 已存在，且有排队或运行中的任务 | 返回该任务，`deduplicated: true` |
| 已存在，最近一次任务成功 | 不新建任务，返回 `status: already_processed` 和当前的 `note_id` |
| 已存在，最近一次任务失败或被取消 | 不自动重试，返回该任务和它的状态，并提示调用 retry |
| 请求带 `reprocess_from` 参数（`acquire` / `transcribe` / `note`） | 新建任务。从指定阶段起忽略缓存重新执行，之前的阶段照常复用。生成新的字幕版本和/或笔记版本 |

导入时如果没有配置在线模型，仍然接受导入，但在返回结果中附带 `warnings: ["MODEL_NOT_CONFIGURED"]`。任务执行到 `note_map` 时会立即失败，不会一直停在运行状态；补好配置后重试即可。

### 7.6 重启恢复

Engine 启动时执行以下步骤：

1. 处于 `running` 的阶段改回 `pending`。处于 `cancelling` 的任务直接改为 `cancelled`。
2. 处于 `running` 的任务改为 `interrupted` 并记录事件；如果开启了自动续跑，再改为 `queued`。
3. 清理孤立的临时文件和过期的上传文件。按 `child_processes` 表核对残留的子进程，只有 PID 和可执行文件路径都匹配时才终止它。
4. 调度器启动后，按正常规则续跑。已经完成的 map 块直接复用。

### 7.7 错误对象与错误码（契约）

```json
{
  "error": {
    "code": "MODEL_AUTH_FAILED",
    "message": "在线模型鉴权失败（HTTP 401）",
    "stage": "note_map",
    "retryable": true,
    "user_action_required": true,
    "hint": "在设置中更新 API Key 后重试该任务",
    "details": {"http_status": 401}
  }
}
```

两个标志的含义：

- `retryable`：调用 retry 后有可能成功（可能需要用户先修正条件）。
- `user_action_required`：需要用户先修改配置、网络或输入，否则重试不会成功。

| 错误码 | 含义 | retryable | 需用户处理 |
| --- | --- | --- | --- |
| `INVALID_ARGUMENT` | 参数无效 | 否 | 是 |
| `NOT_FOUND` | 对象不存在 | 否 | 是 |
| `CONFLICT` | 当前状态不允许该操作 | 否 | 是 |
| `PATH_NOT_ALLOWED` | 本地路径不在允许的导入根目录内 | 否 | 是 |
| `UNSUPPORTED_SOURCE` | 不支持的链接，或不是单个视频 | 否 | 是 |
| `SOURCE_UNAVAILABLE` | 视频不存在、私有、需要登录或受地区限制 | 否 | 是 |
| `SOURCE_BLOCKED` | 平台风控、频率限制或机器人验证 | 是 | 是 |
| `NETWORK_ERROR` | 网络错误，自动重试已耗尽 | 是 | 否 |
| `TOOL_MISSING` | 工具或模型未就绪，且不允许自动准备 | 是 | 是 |
| `TOOL_FAILED` | 外部工具以非零状态退出 | 是 | 否 |
| `CHECKSUM_MISMATCH` | 下载文件的校验和不符 | 是 | 否 |
| `MEDIA_INVALID` | 无法解析媒体文件 | 否 | 是 |
| `NO_AUDIO_STREAM` | 没有音轨（v0 不支持纯画面视频） | 否 | 是 |

## 8. 语音转写

### 8.1 提取音频

```text
ffmpeg -nostdin -hide_banner -y -i <source> -map 0:a:0 -vn -ac 1 -ar 16000 -c:a pcm_s16le <audio.wav.tmp>
```

- **时间偏移**：`timeline_offset_ms = round((音频流的 start_time − 容器的 start_time) × 1000)`，记录在字幕版本中，所有片段时间都加上这个偏移。S-11 会用起始时间非零的样例验证它与播放器 `currentTime` 是否一致。
- **多音轨**：默认使用第一条音轨，v0 不提供选择。

### 8.2 调用 whisper-cli

1. **确定语言**：配置为 `zh` 或 `en` 时直接使用；配置为 `auto` 时，先运行一次语言检测，再把检测结果写入字幕版本。
2. **正式转写**：

   ```text
   whisper-cli -m <model> -f audio.wav -l <lang> -t <threads> -oj -of <out> -pp \
     [--prompt "<提示词>"] [--vad --vad-model <silero 模型>]
   ```

   - 语言为 `zh` 时，提示词是“以下是普通话课程的转写，使用简体中文和标点。”；语言为 `en` 时，提示词是 “The following is a lecture transcript, with proper punctuation and capitalization.”（S-06 实测：large-v3-turbo 不加提示词时可能输出全小写、无标点的英文）。
   - 线程数默认取物理核心数，上限 8。
   - 解析进度输出，更新阶段进度。
   - 具体参数名以锁定版本的 whisper.cpp 为准，在 S-06 中核对。
3. **后处理**：
   - 去掉首尾空白，丢弃空文本片段。
   - 连续 3 次或以上完全相同的片段（常见的重复幻觉）折叠为一个，折叠次数记入字幕元数据。
   - 保证 `start_ms < end_ms`，且片段时间单调不减。
   - whisper 的原始输出 JSON 原样保留。

### 8.3 模型

| 清单 ID | 文件 | 用途 |
| --- | --- | --- |
| `whisper-large-v3-turbo-q5_0` | `ggml-large-v3-turbo-q5_0.bin` | 默认候选，中英文质量与速度较平衡 |
| `whisper-small-q5_1` | `ggml-small-q5_1.bin` | 低配机器候选 |
| `silero-vad` | whisper.cpp 提供的 VAD 模型 | 启用 VAD 时需要 |

- 每个平台的默认模型，在 S-06 中根据参考机实测速度确定，并写入发行说明。
- 模型来自 Hugging Face 上的 whisper.cpp 官方模型仓库，URL 锁定到具体 revision。
- 支持用 `download.mirrors` 走镜像，也支持用 `watchink tools import-model <清单 ID> <文件>` 导入本地文件（同样校验 sha256）。

## 9. 笔记生成与引用

### 9.1 分块

- **切分规则**：按顺序累加字幕片段，直到估算 token 数达到 `note.chunk_max_tokens`（默认 3000），或时长达到 `note.chunk_max_duration`（默认 10 分钟）。在不超过上限的前提下，优先在片段间隔 ≥ 1.5 s 的位置切开。单个片段不拆分。
- **token 估算**：每个 CJK 字符算 1，其余文本按空白分词后的词数 × 1.3。只用于切块，不要求精确。
- **上下文**：每块附带上一块末尾约 30 s 的片段，只用于理解上下文，不允许引用。
- **编号**：提示词中用 `S<idx>` 表示片段（`idx` 为片段在字幕版本中的序号，从 1 开始），由程序映射回片段 ID。

### 9.2 map（每块调用一次模型）

输入包括：视频标题、块序号与时间范围、上下文片段（标明“不可引用”）、可引用片段（格式如 `S123 [12:01–12:08] 文本`）。

输出结构（JSON Schema 由 Go 结构体生成）：

```json
{
  "chunk_summary": "本块主要内容，2–4 句",
  "points": [
    {
      "title": "不超过 30 字",
      "detail": "1–4 句说明",
      "kind": "concept",
      "cites": ["S123", "S124"]
    }
  ],
  "terms": [
    {"term": "术语原文", "explanation": "中文解释", "cites": ["S125"]}
  ]
}
```

`kind` 的取值为 `concept`、`definition`、`method`、`example`、`conclusion`、`caution`、`other`。

校验规则：

- 每个要点至少 1 个、至多 5 个引用，且必须落在本块的可引用范围内。
- 移除无效引用；移除后没有引用的要点被丢弃。两者都计入 coverage。
- 如果 JSON 无法解析，或超过 30% 的要点被丢弃，就附上错误说明发起一次修复调用。修复后仍失败，则该块失败（`MODEL_OUTPUT_INVALID` 或 `CITATION_INVALID`），任务进入可重试的失败状态。
- 有效语音少于 200 个汉字（或 50 个英文词）的块，允许没有要点。
- 输出被截断（`finish_reason=length`）或返回上下文超限时，把该块对半拆分后重试，最小拆到 1 分钟。仍失败则报 `MODEL_OUTPUT_INVALID`。
- 要点 ID 由程序分配，格式为 `P<块序号>.<序号>`。

### 9.3 reduce

输入包括：视频标题与时长、各块摘要、全部要点（ID、标题、说明、时间）。

输出：

```json
{
  "title": "笔记标题",
  "overview": {"text": "200–400 字概览", "point_ids": ["P1.2", "P3.1"]},
  "sections": [
    {"heading": "章节标题", "summary": "1–3 句", "point_ids": ["P1.1", "P1.2"]}
  ],
  "key_takeaways": [
    {"text": "一句话结论", "point_ids": ["P2.3"]}
  ]
}
```

校验与补全：

- 移除不存在的要点 ID。同一个要点只保留它第一次出现的位置。
- 没被放进任何章节的要点，按时间追加到时间范围最接近的章节末尾；如果一个章节都没有，就新建“其他要点”章节。这样保证每个有效要点都会出现在笔记里。
- 概览和每条结论都至少要引用 1 个要点，否则丢弃该条结论。概览为空时，用各块摘要拼接作为兜底，并加上标记。
- 章节的时间范围，取它所含要点引用时间的最小值和最大值。
- 要点超过 120 个，或估算输入超过 12k token 时，改为两级 reduce：
  1. 按时间顺序把块分组（每组最多 60 个要点），每组分别 reduce 出章节。
  2. 对所有组的章节做一次最终 reduce，只产出标题、概览和结论；需要合并相邻章节时，通过列出章节 ID 来表达。

### 9.4 渲染（规范 Markdown）

```markdown
---
watchink:
  video_id: vid_01JA…
  note_id: note_01JA…
  transcript_id: tr_01JA…
  source: https://www.youtube.com/watch?v=…
  duration: "1:02:33"
  language: zh
  generated_at: 2026-10-09T12:00:00Z
  model: openai-compatible/<模型名>
  prompt_version: note-v0.1
---

# <标题>

> 来源：[<视频标题>](<来源链接>) · 时长 1:02:33

## 概览

<概览正文> [0:01:23](wk://seg/seg_…_00012) [0:14:05](wk://seg/seg_…_00133)

## 1. <章节标题> `0:00:00–0:12:40`

<章节摘要>

- **<要点标题>**：<说明> [0:03:12](wk://seg/seg_…_00031)

## 关键结论

- <结论> [0:41:10](wk://seg/seg_…_00402)

## 术语

| 术语 | 说明 | 出处 |
| --- | --- | --- |
| <术语> | <解释> | [0:05:10](wk://seg/seg_…_00050) |
```

- 视频时长 ≥ 1 小时时，时间显示为 `H:MM:SS`，否则为 `MM:SS`。
- 引用指向片段的起始时间。
- 一个要点有多个引用时，按时间顺序列出。

### 9.5 引用校验

每个渲染出来的 `wk://seg/` 链接，都对应 `citations` 表中的一行。`note_render` 的最后一步会重新解析生成的 Markdown，并确认以下三点：

1. 所有链接都能解析为本字幕版本中的片段。
2. 时间位于 `[0, duration_ms]` 之内。
3. 链接与表中的记录一一对应。

任何一项不满足，阶段都以 `INTERNAL` 失败，因为这属于程序缺陷，不是模型问题。

### 9.6 coverage 元数据

```json
{
  "chunks": 7,
  "chunks_empty": 0,
  "points": 54,
  "points_dropped": 2,
  "points_unplaced": 3,
  "citations": 131,
  "citations_dropped": 4,
  "repair_calls": 1,
  "split_retries": 0,
  "transcript_segments": 612,
  "transcript_chars": 15840
}
```

coverage 显示在笔记的信息面板中，也随 `get_note` 结果一起返回，作为 V0-A05 “无静默截断”的证据。

### 9.7 导出改写

| 格式 | 内容 | `wk://seg` 链接的处理 |
| --- | --- | --- |
| `md` | 可移植 Markdown | YouTube 改写为 `https://www.youtube.com/watch?v=<id>&t=<秒>s`；Bilibili 改写为 `https://www.bilibili.com/video/<BV>?p=<n>&t=<秒>`；本地文件改写为纯文本 `[MM:SS]` |
| `md-raw` | 规范 Markdown | 保留原样 |
| `json` | 结构化笔记，含引用表和 coverage | — |
| `srt`、`vtt`、`txt` | 字幕 | — |

导出文件名为 `<净化后的标题>-<video_id 后 6 位>.<扩展名>`。

### 9.8 提示词与在线模型调用

- **提示词管理**：
  - 提示词模板用 `go:embed` 打包。`prompt_version`（例如 `note-v0.1`）随内容变化递增，并参与指纹计算。v0 不支持用户自定义模板。
  - 字幕文本放在用户消息的分隔块中。系统提示声明：字幕里出现的任何指令，都只是待整理的内容。
  - 模型不会获得任何工具。
- **请求**：`POST {base_url}/chat/completions`。`temperature` 默认 0.2；`max_tokens` 在 map 阶段为 2500，在 reduce 阶段为 4000。
- **结构化输出**：`llm.structured_output=auto` 时，依次尝试 `json_schema`、`json_object`、仅靠提示词。某一级别被服务端拒绝后，在本次 Engine 运行期间，对同一组 `(base_url, model)` 缓存这一降级结果。
- **解析**：先去掉 Markdown 代码围栏和 `<think>…</think>` 片段，再严格解析。
- **重试**：
  - 429 遵循 `Retry-After`。
  - 429、5xx、超时、连接错误按指数退避重试（从 1 s 开始，带抖动），最多 5 次。
  - 401、403、404 不重试，立即失败。
- **参数自愈**：与任务内容无关的参数问题不应让任务失败。客户端遇到下列情况时自动调整参数并重试，把调整记为警告（Engine 日志，以及 `job_events` 中的 `stage.warning`），并在本次 Engine 运行期间对同一组 `(base_url, model)` 记住有效的取值：
  - 输出被截断（`finish_reason=length`，推理模型把输出额度用在思考上时很常见）：把输出上限依次提高到 2 倍、4 倍，仍被截断则取消上限；之后才轮到 §9.2 的拆块。
  - 接口只接受 `max_completion_tokens`：改用该参数。
  - 接口拒绝当前的输出上限：降到报错信息给出的上限，没有给出时减半。
  - 接口拒绝 `temperature`：改用模型默认值。
  - 单次请求超时：把超时依次延长到 2 倍、4 倍。
- **并发**：单个任务最多 3 个 map 请求并行，全局受 `llm` 信号量限制（默认 4）。
- **数据外发**：只发送字幕文本、视频标题和时长。设置页和首次配置向导中会明确说明这一点。

## 10. 播放与时间定位

### 10.1 播放策略（`playback` 阶段）

| 源文件 | 处理 |
| --- | --- |
| MP4 / MOV / M4V 容器，视频 H.264，音频 AAC 或 MP3 | 直接使用源文件，不生成新文件 |
| 其他容器（MKV、FLV、TS、WebM 等），编码同上 | 用 `ffmpeg -c copy -movflags +faststart` 重封装 |
| 视频为 H.264，音频不兼容 | 视频直接复制，音频转为 AAC 128 kbps |
| 视频编码不兼容（HEVC、VP9、AV1 等） | 转码为 H.264（`libx264 -preset veryfast -crf 26`，高度上限 720）加 AAC |

yt-dlp 下载时，格式策略优先选择 H.264 + AAC、高度不超过 1080 的版本，以减少转码。转码时不能使用会平移时间戳的参数，这一点由 S-11 验证。

### 10.2 媒体访问

- `GET /api/v1/videos/{id}/playback` 返回 `{url, mime, expires_at}`。其中的 URL 带有 HMAC 签名的短期令牌，默认有效期 6 小时，只授权访问这一个视频的播放文件。
- `GET /media/{video_id}/playback?mt=<令牌>` 由 `http.ServeContent` 处理，支持 Range 请求和条件请求。

### 10.3 跳转

- 前端拦截笔记中的 `wk://seg/<id>` 链接，从引用表查到 `start_ms`，然后把播放器定位到该时间，同时让字幕面板滚动到对应片段并高亮。鼠标悬停在引用上时，显示片段原文。
- 在字幕面板中点击任意片段，同样会跳转；播放过程中，当前片段保持高亮。
- 路由 `/videos/:id?t=<ms>` 打开后直接定位到指定时间。Video DTO 中的 `web_url` 字段使用这种格式，供 CLI 和 MCP 返回给用户。

### 11.2 来源

| 工具 | macOS arm64 | Windows amd64 | Linux amd64 | 许可与分发 |
| --- | --- | --- | --- | --- |

需要 GPL 版 FFmpeg，是因为转码要用 libx264。由于是运行时从上游下载、本项目不做分发，Watchink 自身的许可证不受影响。如果将来改为由我们镜像分发，必须同时履行 GPL 的源码提供义务（见 §20 待决事项）。

### 11.3 安装流程

1. 下载到 `tools/.staging/`。
2. 校验 sha256。
3. 解压。
4. 设置可执行权限。
5. 运行 `--version` 做冒烟测试。
6. 原子移动到 `tools/<name>/<version>/`。
7. 写入 `tools/installed.json`。

任何一步失败，都不影响已经安装的版本。程序永远不会执行未通过校验的文件。内嵌的 whisper-cli 释放流程相同，只是跳过下载这一步。

### 11.4 镜像、代理与本地导入

- `download.mirrors`：按主机名改写下载 URL，例如使用 Hugging Face 镜像。sha256 校验照常进行，所以镜像无法篡改内容。
- `network.proxy`：同时作用于 Go 发起的下载、在线模型请求，以及 yt-dlp（通过 `--proxy` 传入）。为空时遵循 `HTTPS_PROXY` 等环境变量。
- `watchink tools import <name> <文件>`：导入手动下载的文件，同样要校验。

### 11.5 yt-dlp 的调用与更新

调用方式：

```text
yt-dlp --no-playlist --no-mtime --newline --ffmpeg-location <dir> \
  [--js-runtimes deno:<path>] -f <格式策略> --progress-template <机器可读模板> \
  -o <输出模板> -- <规范化 URL>
```

- 只有 YouTube 链接才传入 `--js-runtimes`。
- 不传入 cookies，也不读取浏览器的 cookies。

YouTube 等平台变化频繁，固定的 yt-dlp 版本可能失效。`watchink tools update yt-dlp` 会获取最新的官方 release 及其 `SHA2-256SUMS`，校验通过后作为新版本安装；旧版本保留，可以回退。遇到 `SOURCE_BLOCKED` 或提取器错误时，错误提示会建议执行更新。v0 不做自动更新。

## 13. 接口契约

### 13.1 通用约定（契约）

- JSON 字段使用 snake_case。
- 相对视频的时间统一用 `*_ms` 整数，时刻统一用 RFC 3339 UTC 字符串。
- 分页：`limit`（默认 20，上限 100）加不透明的 `cursor`；返回 `next_cursor`，没有更多时为 `null`。
- 长文本：`max_chars`（默认 20000）加 `offset`；返回 `total_chars` 和 `next_offset`。
- 失败时统一返回 §7.7 的错误对象。
- HTTP 路径带 `/api/v1` 前缀；engine.json 中的 `api` 字段表示接口主版本。

### 13.3 事件流

`GET /api/v1/events` 返回 `text/event-stream`。前端用 fetch 流式读取，这样可以携带 `Authorization` 头。

| 事件 | 数据 |
| --- | --- |
| `job.updated` | Job 对象（含 `rev`） |
| `video.updated` | Video 对象 |
| `tools.updated` | 工具与模型状态 |
| `engine.stopping` | `{reason}` |

- 每 15 s 发送一行注释作为心跳。
- 事件 ID 单调递增。断线重连时带上 `Last-Event-ID`；Engine 缓存最近 1000 条事件，如果客户端请求的事件已超出缓存，客户端应全量刷新。

### 13.5 MCP

- 服务器名为 `watchink`，版本号与程序一致。
- 工具名、描述和 `instructions` 使用英文，因为这是面向 agent 的契约；`message` 和 `hint` 沿用中文。
- `instructions` 中写明标准用法：
  1. 调用 `import_video` 后立即返回。
  2. 用 `get_job` 加 `wait_seconds` 轮询。
  3. 完成后用 `get_note` 读取笔记，再用 `get_transcript` 按 `segment_ids` 或时间区间核对引用。

| Tool | 输入 | 输出 | 注解 |
| --- | --- | --- | --- |
| `import_video` | `source`（绝对路径或 URL）、`language?`、`reprocess_from?` | 与 HTTP 导入响应相同 | 幂等（依赖去重） |
| `get_job` | `job_id`、`wait_seconds?`（0–30）、`after_rev?` | Job | 只读 |
| `cancel_job` | `job_id` | Job | 幂等，不破坏数据 |
| `retry_job` | `job_id` | Job | |
| `list_videos` | `limit?`、`cursor?`、`title_contains?` | `{videos, next_cursor}` | 只读 |
| `get_note` | `video_id`、`format?`（`markdown` / `json`）、`offset?`、`max_chars?` | `{note_id, title, format, content, total_chars, next_offset, citations, coverage}` | 只读 |
| `get_transcript` | `video_id`，加上 `start_ms?` / `end_ms?` 或 `segment_ids?`，以及 `max_chars?` | `{transcript_id, language, segments, truncated, next_start_ms}` | 只读 |
| `export_note` | `video_id`、`format`、`inline?` | `{path, filename, bytes, sha256, content?}`：文件只写到 `<data>/exports/` 下；小于 `max_chars` 时同时内联返回内容 | 只写数据目录 |

行为约定：

- 所有结果都通过 `structuredContent` 返回，同时把相同 JSON 序列化为文本内容，以兼容不支持结构化结果的客户端。
- 业务错误以 `isError: true` 的工具结果返回，内容为 §7.7 的错误对象。
- 使用本地路径的 `import_video` 同样受 `security.import_roots` 限制。
- MCP 进程的 stdout 专用于协议，日志只能写 stderr。
- MCP 客户端断开后，已提交的任务继续执行。

客户端接入方式：命令为 `<可执行文件> mcp`，以 stdio 方式运行。桌面应用的“Agent 接入”页会给出可执行文件的绝对路径，以及常见客户端（如 Claude Code、Claude Desktop）的配置片段。各客户端的具体配置格式，在 P3 阶段按当时的官方文档核对。

### 13.6 桌面绑定（Wails）

| 方法 | 说明 |

## 15. 安全与隐私

- **网络**：只监听 127.0.0.1，v0 不提供修改监听地址的选项。
  - 校验 `Host` 头必须是 `127.0.0.1:<port>` 或 `localhost:<port>`，以防 DNS rebinding。
  - 桌面、CLI、MCP 一律携带 Bearer 令牌。
  - Web 界面可选且没有登录：`web.enabled` 关闭（默认）时，不带令牌的请求一律拒绝，页面本身也不提供；开启时，不带令牌的请求只有在不是跨站请求（`Sec-Fetch-Site` 不为 `cross-site` / `same-site`，且 `Origin` 为空或等于自身）时才放行，状态变更请求还必须带有等于自身的 `Origin` 和自定义头 `X-WK-Request: 1`。
  - 取舍：开启 Web 界面后，这台电脑上的任何本地程序都可以不带令牌读写 Engine 的接口；其他网站仍然不能（跨站请求被拒绝，CORS 也不放行）。这是为了免登录而接受的风险，所以默认关闭，由用户在桌面应用里显式开启。
  - CORS 只放行 Wails 的 WebView 来源，具体来源值在 S-04 中确认。
- **令牌**：每次启动 Engine 时生成 32 字节随机数，保存在 engine.json 中（权限 0600）。
- **路径**：
  - 导入的本地路径必须是绝对路径，并且解析符号链接后仍位于 `security.import_roots` 之内。
  - Engine 只在 `<data>` 内写文件。
  - `RevealInFileManager` 只接受 `<data>` 下的路径。
- **外部命令**：只用参数数组启动，不经过 shell；URL 必须先规范化，并且在 YouTube / Bilibili 主机名白名单内，再放在 `--` 之后传给 yt-dlp。
- **模型输出**：只接受 JSON，并通过结构校验。渲染时禁用原始 HTML，链接只允许 `wk://`、`https://` 和 `http://`。字幕中的指令不会改变任何权限，因为模型本身没有工具可用。
- **凭据**：日志和错误详情中的 Authorization 头、API Key、令牌统一脱敏。导出文件和 `config show` 中不包含凭据。V0-A10 会通过搜索日志和导出文件来验证。
- **数据外发**：只把字幕文本、标题和时长发给用户配置的在线模型；不发送音频或画面。v0 不收集任何遥测数据。

### 16.5 S-02：Windows 子系统方案

| 方案 | 做法 | 风险 |
| --- | --- | --- |
| a | 单个 GUI 子系统 exe；CLI 和 MCP 模式下调用 `AttachConsole(ATTACH_PARENT_PROCESS)` | 在交互式 cmd 或 PowerShell 中，shell 可能不等待进程结束，导致输出与提示符交错 |
| b | 单个控制台子系统 exe；以桌面模式启动时调用 `FreeConsole()` | 双击启动时会闪现一下控制台窗口 |

1. 双击启动时不出现控制台窗口。
2. 在 cmd 和 PowerShell 中执行 `watchink jobs list --json`，shell 会等待命令结束，输出完整，管道可用。
3. 真实 MCP 客户端以 stdio 方式连接正常。

按 a → c → b 的顺序，选第一个满足全部标准的方案。

### 17.2 伪造提供方与故障注入

- 测试构建（`-tags testfakes`）通过环境变量 `WATCHINK_FAKES=asr,llm,download` 启用伪造实现，读取 `testdata/fakes/` 中的脚本化响应。脚本可以模拟非法 JSON、401、429、上下文超限、输出截断等情况。
- 测试构建（`-tags faultinject`）通过 `WATCHINK_FAULTS="acquire:fail_once,note_map:kill_engine_after=2"` 在指定阶段注入失败，或在某处终止 Engine。
- 发布构建不包含上述两个标签。验收中的失败场景（V0-A07）一律用真实条件制造：断开网络、使用错误的 Key、在 `note_map` 阶段手动终止 Engine。

### 17.3 评测样例

供 V0-A03 到 V0-A05 使用：

- 在 `testdata/eval/v0/` 中维护样例清单（`samples.yaml`）：来源、sha256、时长、语言、许可说明，以及预先标注的知识点（每个知识点包含时间区间和描述）。
- 媒体文件不提交到仓库，用脚本按清单获取并校验。
- 必须包括：一段 5–15 分钟的中文课程、一段 5–15 分钟的英文课程（各标注 10 个知识点）；一段 60 分钟以上的课程（前、中、后段各标注 3 个知识点）。
- 标注在开始生成笔记之前完成，不能参考模型输出。
- 评分表模板放在 `docs/acceptance/templates/`，填写后的评分表随验收记录一起保存。

| V0-A05 长视频 | 60 分钟以上的样例：按前、中、后三段统计标注知识点的覆盖情况，并附上 coverage 元数据和完整的转写产物 |
| V0-A06 四入口真实闭环 | 每个入口各独立提交一次并完成；再用另一个入口按相同 ID 读取结果。Web 用独立浏览器，MCP 用真实客户端，均附截图或记录 |
| V0-A07 失败与恢复 | 在真实条件下分别制造三种失败：下载时断网、使用无效的 Key、在 `note_map` 阶段终止 Engine。修复后重试，用阶段的 `reused=true` 和产物数量证明没有重复执行 |
| V0-A08 取消与重启 | 测量从发出取消到所有子进程退出的时间；重启后检查任务状态和续跑结果 |
| V0-A09 单一调度所有者 | 桌面加两个客户端（CLI 和 MCP）同时导入相同和不同的视频。确认只有一个 Engine、重复请求按 §7.5 处理、数据库完整性检查通过 |
| V0-A10 导出与保留 | 用其他工具打开导出的 Markdown 和字幕；替换程序文件后读取原数据；在日志和导出文件中搜索 Key 和令牌，确认不存在 |

## 20. 风险与待决事项

### 20.1 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| YouTube 风控或机器人验证，yt-dlp 失效 | V0-A02 的 YouTube 样例失败 | 提供 `tools update yt-dlp`；用 `SOURCE_BLOCKED` 明确报错；验收记录注明日期与网络环境；v0 不使用 cookies |
| Bilibili 风控（412 等） | 同上 | 同上，并控制请求频率 |
| Windows / Linux 上 CPU 转写速度慢 | 长视频处理时间长 | 根据 S-06 实测选择各平台默认模型；界面显示进度；GPU 加速放到 v2 |
| Whisper 幻觉，繁简混杂 | 字幕质量 | 启用 VAD、使用提示词、折叠重复片段；笔记统一由模型整理为简体中文 |
| 兼容端点的结构化输出存在差异 | 笔记生成失败 | 三级降级加修复调用；用 S-10 的支持矩阵指导配置 |
| WebView 跨源访问或 ATS 限制 | 桌面端不可用 | D-04 的回退方案 |
| 杀毒软件拦截内嵌后释放的可执行文件 | 无法转写 | 代码签名；回退为下载 |
| 未签名应用被 Gatekeeper 或 SmartScreen 拦截 | 首次启动受阻 | 申请证书；拿不到证书时，在发行说明中写清操作步骤 |
| Linux 发行版之间的差异 | 依赖缺失 | 只承诺经过实测的 Ubuntu 24.04；列出包名；提供 nogui 构建 |
| 在中国大陆访问 GitHub 或 Hugging Face 不稳定 | 工具准备失败 | 镜像与代理配置；支持本地导入 |
| Wails v2 进入维护期 | 长期维护风险 | Wails 相关代码隔离在一个目录内；v1 开始前复评 |
| 磁盘占用 | 用户磁盘空间 | 默认删除 WAV；完整的存储管理在 v2 |
