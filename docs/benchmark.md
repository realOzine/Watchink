# 性能基准与压测

测量日期：2026-10-10。本文记录基准的设计、一次优化前后的实测结果，以及如何复现。

> **后续变化（2026-10-10）**：下文“改了什么”的第 2 项（引用表和字幕的内存缓存）已经移除。复查时的判断是：单用户的本机应用到不了这个瓶颈，缓存带来的共享状态不值得保留。批量查询和字幕导出的优化仍在。
>
> 移除后重新测了一次热访问（同样的机器和参数，每个场景 3 秒）：资料库列表 5,014 req/s，读笔记 6,084，完整字幕 2,943，SRT 导出 2,939，字幕时间窗口 12,338，混合负载 4,495 req/s、p95 16 ms。也就是说，读笔记和完整字幕回到了优化前的水平，列表和 SRT 导出保持提升。下文表格里“优化后”一列中这两类接口的数字不再成立，保留它们是为了记录当时的测量。

## 结论

- 读接口在“热”访问下吞吐提高到约 2.3 倍（混合负载 4,338 → 9,851 req/s），p95 从 34.6 ms 降到 6.3 ms。
- 提升最大的是读笔记、读完整字幕和导出字幕（4–5 倍）；资料库列表约 1.9 倍。
- “冷”访问（每个请求都是该视频的第一次请求）下缓存不起作用：读笔记和完整字幕基本不变，只有列表和字幕导出仍有提升。
- 后台持续写入时，读性能和上面基本一致，写入速率没有明显变化。
- 写入路径和调度器没有优化，前后数值相同：它们离实际需要还很远，没有动的理由。

对一个单用户的本地应用来说，优化前的数字已经够用。这次优化消除的是三处明确的浪费，不是为了某个目标值。

## 测的是什么

基准代码在 `internal/bench`，分两部分：

| 部分 | 命令 | 内容 |
| --- | --- | --- |
| 微基准 | `go test -run '^$' -bench . -benchmem ./internal/bench` | 每个读接口的端到端耗时与内存分配；一次转写入库；调度器每个任务的自身开销；长字幕的文本处理 |
| 压测 | `go run ./internal/bench/cmd/loadtest` | 多个并发客户端持续请求，输出每个接口和混合负载的吞吐与 p50 / p95 / p99 / 最大延迟 |

两者都跑在**真实的组件**上：真实的 `service`、真实的 HTTP 处理器（含鉴权和 Host 校验）、真实的 SQLite 文件，数据目录是临时生成的。只有监听端口用的是测试服务器。没有涉及外部工具和在线模型：转写和生成笔记的耗时由 whisper 和模型决定，不在这里测。

**数据**：每个视频带一份字幕（默认 900 个片段，约一小时的课）、一份笔记（60 条引用）和一个已完成的任务。字幕文本是中英混排的句子。

**读负载**（`bench.Endpoints`）对应界面和 Agent 的实际请求：资料库列表、单个视频、笔记、完整字幕、SRT 导出、字幕时间窗口、任务列表、单个任务。

**两种访问模式**：

- **热**：只访问 8 个视频。一个人加一个 Agent 同时处理的视频就是这个量级，引擎的缓存也是按这个规模定的。
- **冷**：轮流访问库里的全部视频，每个请求都是该视频的第一次请求。这是缓存完全帮不上忙的最坏情况，单独报告，避免只展示好看的数字。

**读写混合**（`-writers N`）：N 个后台写入者循环存入完整字幕（引擎里最大的一次写入），通过第二个数据库句柄与引擎竞争 SQLite 的写锁。

## 环境

Apple M3 Pro（11 核），18 GB 内存，macOS 27.0.1，Go 1.27.1。压测参数：200 个视频 × 900 片段，32 个并发客户端，每个场景 4 秒。“优化前”是提交 `85e23e9`，“优化后”是 `901c655` 及之后；两边用同一份基准代码，在机器空闲时先后各跑一次。

## 改了什么

剖析读接口后发现三处浪费：

1. **资料库列表每行一次查询**。列表为每个视频单独查一次播放产物。改为一条批量查询（`store.ListArtifactsOfVideos`）。
2. **反复读取不会变的数据**。读笔记时，约 80% 的时间花在把引用表和片段文本连接出来；读字幕时花在逐行取出片段。字幕版本和笔记版本一经生成就不可变，所以在 `service` 里各加了一个小的 LRU（`service/cache.go`），不需要任何失效逻辑。只读一部分字幕且该字幕不在缓存里时，仍走数据库的索引查询，不会为此加载全部片段。
3. **字幕导出逐条走 `fmt`**。每个片段两次格式化时间、一次格式化整条字幕。改为直接写入预先分配好的缓冲区，文本本来就是单行时跳过重写（`notes/export.go`）。

缓存的第一版有问题，是基准自己暴露的：最初任何未命中都会加载整份字幕，轮流访问 100 个视频时，时间窗口请求反而慢了 4 倍。现在的策略是完整读取才填充缓存，部分读取未命中时回到索引查询。

## 没有做的

- **预编译语句缓存**。剖析显示每次查询约 6% 的时间在重新准备语句。改动面大，收益有限，没有做。
- **任务列表**。两条查询，剩余时间主要是 SQLite 驱动（纯 Go 实现）逐行取数的固有开销。
- **调度器**。每个任务约 1.2 ms 的自身开销来自十几次串行的小事务；真实任务以分钟计，这不是瓶颈。

## 并发正确性

性能改动引入了共享状态（缓存），所以除了测速度，还做了这些检查：

- 全量测试在竞态检测下通过（`go test -race ./...`）。
- 压测的全部读场景和调度器基准在竞态检测下各跑 300 次，没有报告竞态。
- 缓存有专门的并发测试：16 个 goroutine 在容量为 4 的缓存上轮流读 9 个 key，命中、未命中、重复加载和淘汰交错发生。
- `service` 层的并发导入测试：24 个调用者同时导入同一个文件，只产生一个视频和一个任务；12 个不同文件并发导入互不合并。

没有覆盖的：`pipeline` 里并行请求模型和多个任务争用资源名额的场景；真正的多进程竞争（多客户端冷启动是进程内模拟的）；Windows 和 Linux 上的任何运行时行为。

## 复现

```sh
# 微基准
go test -run '^$' -bench . -benchmem -benchtime 2s ./internal/bench

# 压测：热访问 / 冷访问 / 读写混合
go run ./internal/bench/cmd/loadtest -videos 200 -segments 900 -c 32 -d 4s
go run ./internal/bench/cmd/loadtest -videos 200 -segments 900 -c 32 -d 4s -cold
go run ./internal/bench/cmd/loadtest -videos 200 -segments 900 -c 32 -d 4s -writers 2
```

数字受机器负载影响明显：后台有编译任务时，未改动的路径也会有 ±30% 的波动。对比前后版本时，用同一份基准代码、在机器空闲时先后运行。
